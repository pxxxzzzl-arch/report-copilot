# 技术决策记录

每条决策记录：背景、选择、备选方案、理由。决策推翻时不删除旧条目，而是新增一条并注明"取代 D-xxx"。

## D-001 依赖管理用 uv（阶段 0）

- **选择**：uv + `pyproject.toml` + `uv.lock`
- **备选**：pip + requirements.txt；conda
- **理由**：
  - 锁文件 `uv.lock` 固定所有传递依赖的版本，换机器或进 Docker 时能完整复现环境；
  - 安装速度比 pip 快一个数量级，后面 torch 这类重依赖反复装时能省不少时间；
  - 能直接管理 Python 版本（`uv venv --python 3.11`）；本机已有 3.11 时直接复用，没有时自动下载。

## D-002 依赖按阶段逐步引入（阶段 0）

- **选择**：阶段 0 只装 `pydantic-settings` 和 `pytest`，其他库到用到它的阶段再 `uv add`。
- **理由**：torch 和 FlagEmbedding 体积大；提前装会拖慢环境搭建，而且版本可能在用到之前就变了。每个阶段新增了哪些依赖，看 git diff 一目了然。

## D-003 配置用 pydantic-settings 分组嵌套（阶段 0）

- **选择**：`Settings` 下按 paths / llm / embedding / reranker / store / log 分组，环境变量用 `__` 表示层级（如 `LLM__MODEL`）。
- **理由**：
  - 启动时就做类型校验：非法值直接报错，不会等到运行到一半才出问题；
  - 密钥用 `SecretStr`，打印或写日志时不会泄露；
  - 相对路径统一基于项目根目录解析，不受启动时工作目录影响。
- **约定**：检索和切分参数（top_k、k_rrf、chunk_size 等）到对应阶段再加入，不提前猜默认值。

## D-004 结构化日志用标准库 logging + contextvars（阶段 0）

- **选择**：自己写 JSON Formatter + `ContextVar` 保存 trace_id，不引入 structlog / loguru。
- **备选**：structlog（功能更全）、loguru（写法更简洁）
- **理由**：
  - 零新增依赖，第三方库（httpx、qdrant-client 等）的日志也走标准库，格式统一；
  - `ContextVar` 天然适配 asyncio：每个任务有独立的上下文，FastAPI 并发请求时 trace_id 不会串；
  - 需要的功能只有"JSON 输出 + trace_id + 阶段耗时"，一百多行就能写完，也便于讲清楚原理。
- **新增文件**：`common/log.py`（原目录结构中没有，经确认后新增）。

## D-005 开发用基础设施延后到阶段 4（阶段 0）

- **选择**：Qdrant / Postgres / Redis 的开发用 Compose 文件，到阶段 4 第一次用到时再建。
- **理由**：阶段 1~3（数据准备、评测集、评测脚本）用不到这些服务，提前建只会增加维护成本。

## D-006 年报来源与下载方式（阶段 1）

- **选择**：直接调用巨潮资讯网的公开接口（股票列表 + 公告查询），HTTP 用标准库 `urllib`。
- **备选**：手动下载；requests / httpx。
- **理由**：
  - 手动下载无法复现，脚本 + manifest 里的 `source_url`、`sha256` 能说清每份文件从哪来、有没有被改过；
  - 只有两个 GET/POST 接口，标准库足够，不为此新增依赖；
  - 请求间隔 1 秒、有限次重试，尽量不给对方服务器造成压力。
- **语料**：贵州茅台、五粮液、泸州老窖、宁德时代、比亚迪、中芯国际，2024 与 2025 年报，共 12 份。
  三家白酒公司用于跨公司对比题；每家两个年份用于跨年度题；覆盖沪市主板、深市主板、创业板、科创板四种排版。
- **筛选规则**：排除摘要、英文版、已取消、港股公告、更正前；同年多份时优先"更新后 / 更正后 / 修订"，再取最新发布的一份。

## D-007 页码约定：PDF 物理页码（阶段 1）

- **选择**：全项目的 `page` 都是 PDF 物理页序号，从 1 开始。
- **备选**：年报页脚印的页码。
- **理由**：页脚页码与物理页码通常差几页（封面、目录不编页码），且不是每页都有；
  而引用溯源最终要在 PDF 上定位、渲染截图，物理页码可以直接用，不需要换算。
- **影响**：阶段 2 标注 `gold.page` 时，以 PDF 阅读器显示的页码为准，不看页脚。

## D-008 PDF 预检方法与结论（阶段 1）

- **方法**：逐页统计字符数、图片覆盖面积占比（矩形并集面积，重叠只算一次）、乱码字符占比，
  按阈值分为 text / scanned / blank / garbled。阈值在 `config.py` 的 `PrecheckSettings` 中。
- **结论**（真实输出见 `data/precheck_summary.csv`）：
  - 12 份共 2425 页，**全部为 text 页**，没有扫描页、空白页、乱码页，本批语料不需要 OCR。
  - 字符最少的页是封面和"适用 / 不适用"声明页（最少 31 字），图片占比最高 0.44（泸州老窖的图文混排页），都远离误判区间，初始阈值无需调整。
  - 局限：真实语料里没有扫描页和乱码页，这两个分支目前只由合成 PDF 的单元测试覆盖。
- **发现：符号字体字符**（530 页出现，单页占比最高 3.5%）：
  - `U+F052`（Wingdings 2）是勾选框 ☑，出现在"□适用 ☑不适用"中，**带有语义**；
  - `U+F0A3`（Wingdings 2）是比亚迪 2025 年版的勾选框，具体对应 ☑ 还是 □ 需要渲染页面核对；
  - `U+F06C`（Wingdings）是列表圆点 ●。
  - 这些字符落在 Unicode 私用区，直接抽取会丢失"哪一项被勾选"的信息。**解析阶段需要加一张符号字体映射表**。
- **局限**：乱码指标只能发现无效码位。字体映射错误导致抽出"合法但错误的汉字"的情况，这个指标查不出来，只能靠抽样人工核对（本次抽样未发现）。

## D-009 评测集 gold 增加 `alt`（等价位置）（阶段 2）

- **问题**：同一个数字在年报中会出现多次（主要会计数据、合并报表、附注、下一年年报的上年同期列）。
  只标一处，召回了其他同样正确的位置也会被判为未命中，指标会被系统性低估；把这些位置都列为独立的 gold，又会被当成"必须全部召回"，压低 Recall。
- **选择**：每条 gold 是一份必需证据，可选 `alt` 列出等价位置，命中任意一个即算命中；Recall 的分母仍是 gold 条数。
- **备选**：每条 gold 只标一个主位置。代价是指标偏低，而且偏低多少说不清。
- **收录标准**：同主体、同期间、同指标标签下的同一 span。数字相同但含义不同的位置不收（研发费用 ≠ 研发投入，技术人员 ≠ 研发人员），见 `eval/goldset_schema.md` 4.2 节。
- **过程中的教训**：对短而常见的数字（如 `1,098`），"默认全收"会误收大量无关子串，必须逐条看上下文。

## D-010 归一化函数放在 `common/text.py`（阶段 2）

- **选择**：`normalize()`（全角转半角 + 去空白）放在公共模块，评测集校验、检索命中判定、以后的引用校验都调用这一个实现。
- **理由**：如果这几处的归一化规则稍有不同，就会出现"校验通过、评测却判未命中"这类难以排查的问题。

## D-011 NDCG 采用"按 gold 去重"的增益（阶段 3）

- **问题**：普通的二元 NDCG 里，同一页被切成多个 chunk 并包揽前几名时，NDCG 会接近 1；
  但多证据题（比较、计算）真正需要的是覆盖全部 gold，这时其实只找到了 1 条。
- **定义**：第 i 名的增益 = 它新覆盖的 gold 条数（前面已经覆盖的 gold 不再计分），折损为 1/log2(i+1)；
  IDCG 假设前 min(K, gold 条数) 个位置各覆盖 1 条新 gold；结果截断为 1。
- **为什么要截断**：最初确认的是二元增益（新覆盖记 1）。实现时发现，两条 gold 在同一页时（q037、q040、q041、q042、q044），
  一个 chunk 就能同时覆盖两条，二元增益下 NDCG 最高只有 0.61，最好的检索反而拿不到满分。
  改成按"新覆盖条数"计增益后，DCG 可能超过 IDCG，这时已经是最优，截断为 1。
- **与教科书定义的区别**：相关性以 gold 为单位，而不是以 chunk 为单位。面试时要能讲清楚这个取舍。

## D-012 用合成检索器检验评测流程（阶段 3）

- **做法**：oracle 直接返回 gold 所在页，random_page 随机返回页面，都在真实评测集上运行。
- **理由**：先用"已知答案"的输入检验测量工具本身，再用它去测检索器。
  如果 oracle 达不到满分，说明命中判定、评测集标注或页面文本之间有不一致，这时的检索指标就不可信。
- **结果**：oracle 除 Precision 外全部 1.0000；random_page 的 Recall@10 为 0.0096。
  oracle 的 Precision@5 = 0.2808 是定义决定的（分母固定为 K，而 oracle 每题只返回 1~3 页）。

## D-013 bge-m3 的获取方式与向量化设备（阶段 4）

- **模型来源**：HuggingFace 经代理只有约 0.1MB/s，ModelScope 直连约 2.9MB/s（用 10MB 分段请求实测）。
  所以从 ModelScope 下载，再用 HuggingFace API 公布的 sha256（大文件）和 git blob 哈希（小文件）逐个校验，12 个文件全部一致。
  只下载推理需要的 12 个文件（约 2.3GB），不下载 onnx 目录（另外 2.3GB）。
- **设备**：64 个 chunk 实测，MPS（fp16）33.4 条/秒，CPU（fp32）4.3 条/秒，快约 8 倍；
  两种设备算出的向量余弦相似度最低 0.99968，fp16 带来的精度损失可以忽略。
  代码里的默认值仍是 cpu（与机器无关），运行时用 `EMBEDDING__DEVICE=mps` 指定；设备会写入评测明细的元信息。
- **注意**：FlagEmbedding 默认只截取 512 个 token（passage_max_length），这里调用时显式传 `max_length=1024` 覆盖。

## D-014 公司/年份过滤：规则识别 + 严格年份口径（阶段 5，E002）

- **识别**：公司名来自 manifest 的公司简称和股票代码，另加少量常用别名（放在配置里）；年份用正则匹配"四位数字 + 年"。
  不用大模型做查询理解：规则的行为可以预测、可以测试，也没有额外延迟；以后遇到规则覆盖不了的问法再升级。
- **年份口径**：严格按问题中的年份过滤（问 2024 年就只查 2024 年报）。
  备选是同时放行下一年的年报（其"上年同期"列也有这些数据），但那样会把 BC-002 的年份混淆带回来。
- **防过拟合检查**：别名表不是从评测集题目里整理出来的；上线前确认过 60 题的过滤条件都不会排除 gold 主位置。
- **已知局限**：问题里没有写公司名时（例如只说"这家公司"），不会做任何过滤；多轮对话的指代要到阶段 7 由 Agent 处理。

## D-015 实验结论的显著性口径（阶段 5）

- 评测集只有 52 道检索题，一题的变化就会让 Hit@5 变动约 0.019，所以不能只比平均值。
- `eval/compare_runs.py` 对两次实验做**配对 bootstrap**（1 万次重抽样，固定种子）和**符号检验**。
- **口径**：均值差的 95% 置信区间不跨 0，才称为"确定提升/下降"；否则写成"方向为正（或负）但不显著"。README 和简历里只写满足这个口径的结论。
