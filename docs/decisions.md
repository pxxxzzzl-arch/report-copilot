# 技术决策记录

每条决策记录：背景、选择、备选方案、理由。决策推翻时不删除旧条目，而是新增一条并注明"取代 D-xxx"。

---

## D-001 依赖管理用 uv（阶段 0）

- **选择**：uv + `pyproject.toml` + `uv.lock`
- **备选**：pip + requirements.txt；conda
- **理由**：
  - 锁文件 `uv.lock` 固定所有传递依赖的版本，换机器或进 Docker 时能完整复现环境；
  - 安装速度比 pip 快一个数量级，后面 torch 这类重依赖反复装时能省不少时间；
  - 能直接管理 Python 版本（`uv venv --python 3.11`）；本机已有 3.11 时直接复用，没有时自动下载。

## D-002 依赖按阶段逐步引入（阶段 0）

- **选择**：阶段 0 只装 `pydantic-settings` 和 `pytest`，其他库到用到它的阶段再 `uv add`。
- **理由**：torch 和 FlagEmbedding 体积大；提前装会拖慢环境搭建，而且版本可能在用到之前就变了。每个阶段新增了哪些依赖，看 git diff 一目了然。

## D-003 配置用 pydantic-settings 分组嵌套（阶段 0）

- **选择**：`Settings` 下按 paths / llm / embedding / reranker / store / log 分组，环境变量用 `__` 表示层级（如 `LLM__MODEL`）。
- **理由**：
  - 启动时就做类型校验：非法值直接报错，不会等到运行到一半才出问题；
  - 密钥用 `SecretStr`，打印或写日志时不会泄露；
  - 相对路径统一基于项目根目录解析，不受启动时工作目录影响。
- **约定**：检索和切分参数（top_k、k_rrf、chunk_size 等）到对应阶段再加入，不提前猜默认值。

## D-004 结构化日志用标准库 logging + contextvars（阶段 0）

- **选择**：自己写 JSON Formatter + `ContextVar` 保存 trace_id，不引入 structlog / loguru。
- **备选**：structlog（功能更全）、loguru（写法更简洁）
- **理由**：
  - 零新增依赖，第三方库（httpx、qdrant-client 等）的日志也走标准库，格式统一；
  - `ContextVar` 天然适配 asyncio：每个任务有独立的上下文，FastAPI 并发请求时 trace_id 不会串；
  - 需要的功能只有"JSON 输出 + trace_id + 阶段耗时"，一百多行就能写完，也便于讲清楚原理。
- **新增文件**：`common/log.py`（原目录结构中没有，经确认后新增）。

## D-005 开发用基础设施延后到阶段 4（阶段 0）

- **选择**：Qdrant / Postgres / Redis 的开发用 Compose 文件，到阶段 4 第一次用到时再建。
- **理由**：阶段 1~3（数据准备、评测集、评测脚本）用不到这些服务，提前建只会增加维护成本。

## D-006 年报来源与下载方式（阶段 1）

- **选择**：直接调用巨潮资讯网的公开接口（股票列表 + 公告查询），HTTP 用标准库 `urllib`。
- **备选**：手动下载；requests / httpx。
- **理由**：
  - 手动下载无法复现，脚本 + manifest 里的 `source_url`、`sha256` 能说清每份文件从哪来、有没有被改过；
  - 只有两个 GET/POST 接口，标准库足够，不为此新增依赖；
  - 请求间隔 1 秒、有限次重试，尽量不给对方服务器造成压力。
- **语料**：贵州茅台、五粮液、泸州老窖、宁德时代、比亚迪、中芯国际，2024 与 2025 年报，共 12 份。
  三家白酒公司用于跨公司对比题；每家两个年份用于跨年度题；覆盖沪市主板、深市主板、创业板、科创板四种排版。
- **筛选规则**：排除摘要、英文版、已取消、港股公告、更正前；同年多份时优先"更新后 / 更正后 / 修订"，再取最新发布的一份。

## D-007 页码约定：PDF 物理页码（阶段 1）

- **选择**：全项目的 `page` 都是 PDF 物理页序号，从 1 开始。
- **备选**：年报页脚印的页码。
- **理由**：页脚页码与物理页码通常差几页（封面、目录不编页码），且不是每页都有；
  而引用溯源最终要在 PDF 上定位、渲染截图，物理页码可以直接用，不需要换算。
- **影响**：阶段 2 标注 `gold.page` 时，以 PDF 阅读器显示的页码为准，不看页脚。

## D-008 PDF 预检方法与结论（阶段 1）

- **方法**：逐页统计字符数、图片覆盖面积占比（矩形并集面积，重叠只算一次）、乱码字符占比，
  按阈值分为 text / scanned / blank / garbled。阈值在 `config.py` 的 `PrecheckSettings` 中。
- **结论**（真实输出见 `data/precheck_summary.csv`）：
  - 12 份共 2425 页，**全部为 text 页**，没有扫描页、空白页、乱码页，本批语料不需要 OCR。
  - 字符最少的页是封面和"适用 / 不适用"声明页（最少 31 字），图片占比最高 0.44（泸州老窖的图文混排页），都远离误判区间，初始阈值无需调整。
  - 局限：真实语料里没有扫描页和乱码页，这两个分支目前只由合成 PDF 的单元测试覆盖。
- **发现：符号字体字符**（530 页出现，单页占比最高 3.5%）：
  - `U+F052`（Wingdings 2）是勾选框 ☑，出现在"□适用 ☑不适用"中，**带有语义**；
  - `U+F0A3`（Wingdings 2）是比亚迪 2025 年版的勾选框，具体对应 ☑ 还是 □ 需要渲染页面核对；
  - `U+F06C`（Wingdings）是列表圆点 ●。
  - 这些字符落在 Unicode 私用区，直接抽取会丢失"哪一项被勾选"的信息。**解析阶段需要加一张符号字体映射表**。
- **局限**：乱码指标只能发现无效码位。字体映射错误导致抽出"合法但错误的汉字"的情况，这个指标查不出来，只能靠抽样人工核对（本次抽样未发现）。

## D-009 评测集 gold 增加 `alt`（等价位置）（阶段 2）

- **问题**：同一个数字在年报中会出现多次（主要会计数据、合并报表、附注、下一年年报的上年同期列）。
  只标一处，召回了其他同样正确的位置也会被判为未命中，指标会被系统性低估；把这些位置都列为独立的 gold，又会被当成"必须全部召回"，压低 Recall。
- **选择**：每条 gold 是一份必需证据，可选 `alt` 列出等价位置，命中任意一个即算命中；Recall 的分母仍是 gold 条数。
- **备选**：每条 gold 只标一个主位置。代价是指标偏低，而且偏低多少说不清。
- **收录标准**：同主体、同期间、同指标标签下的同一 span。数字相同但含义不同的位置不收（研发费用 ≠ 研发投入，技术人员 ≠ 研发人员），见 `eval/goldset_schema.md` 4.2 节。
- **过程中的教训**：对短而常见的数字（如 `1,098`），"默认全收"会误收大量无关子串，必须逐条看上下文。

## D-010 归一化函数放在 `common/text.py`（阶段 2）

- **选择**：`normalize()`（全角转半角 + 去空白）放在公共模块，评测集校验、检索命中判定、以后的引用校验都调用这一个实现。
- **理由**：如果这几处的归一化规则稍有不同，就会出现"校验通过、评测却判未命中"这类难以排查的问题。

## D-011 NDCG 采用"按 gold 去重"的增益（阶段 3）

- **问题**：普通的二元 NDCG 里，同一页被切成多个 chunk 并包揽前几名时，NDCG 会接近 1；
  但多证据题（比较、计算）真正需要的是覆盖全部 gold，这时其实只找到了 1 条。
- **定义**：第 i 名的增益 = 它新覆盖的 gold 条数（前面已经覆盖的 gold 不再计分），折损为 1/log2(i+1)；
  IDCG 假设前 min(K, gold 条数) 个位置各覆盖 1 条新 gold；结果截断为 1。
- **为什么要截断**：最初确认的是二元增益（新覆盖记 1）。实现时发现，两条 gold 在同一页时（q037、q040、q041、q042、q044），
  一个 chunk 就能同时覆盖两条，二元增益下 NDCG 最高只有 0.61，最好的检索反而拿不到满分。
  改成按"新覆盖条数"计增益后，DCG 可能超过 IDCG，这时已经是最优，截断为 1。
- **与教科书定义的区别**：相关性以 gold 为单位，而不是以 chunk 为单位。面试时要能讲清楚这个取舍。

## D-012 用合成检索器检验评测流程（阶段 3）

- **做法**：oracle 直接返回 gold 所在页，random_page 随机返回页面，都在真实评测集上运行。
- **理由**：先用"已知答案"的输入检验测量工具本身，再用它去测检索器。
  如果 oracle 达不到满分，说明命中判定、评测集标注或页面文本之间有不一致，这时的检索指标就不可信。
- **结果**：oracle 除 Precision 外全部 1.0000；random_page 的 Recall@10 为 0.0096。
  oracle 的 Precision@5 = 0.2808 是定义决定的（分母固定为 K，而 oracle 每题只返回 1~3 页）。

## D-013 bge-m3 的获取方式与向量化设备（阶段 4）

- **模型来源**：HuggingFace 经代理只有约 0.1MB/s，ModelScope 直连约 2.9MB/s（用 10MB 分段请求实测）。
  所以从 ModelScope 下载，再用 HuggingFace API 公布的 sha256（大文件）和 git blob 哈希（小文件）逐个校验，12 个文件全部一致。
  只下载推理需要的 12 个文件（约 2.3GB），不下载 onnx 目录（另外 2.3GB）。
- **设备**：64 个 chunk 实测，MPS（fp16）33.4 条/秒，CPU（fp32）4.3 条/秒，快约 8 倍；
  两种设备算出的向量余弦相似度最低 0.99968，fp16 带来的精度损失可以忽略。
  代码里的默认值仍是 cpu（与机器无关），运行时用 `EMBEDDING__DEVICE=mps` 指定；设备会写入评测明细的元信息。
- **注意**：FlagEmbedding 默认只截取 512 个 token（passage_max_length），这里调用时显式传 `max_length=1024` 覆盖。

## D-014 公司/年份过滤：规则识别 + 严格年份口径（阶段 5，E002）

- **识别**：公司名来自 manifest 的公司简称和股票代码，另加少量常用别名（放在配置里）；年份用正则匹配"四位数字 + 年"。
  不用大模型做查询理解：规则的行为可以预测、可以测试，也没有额外延迟；以后遇到规则覆盖不了的问法再升级。
- **年份口径**：严格按问题中的年份过滤（问 2024 年就只查 2024 年报）。
  备选是同时放行下一年的年报（其"上年同期"列也有这些数据），但那样会把 BC-002 的年份混淆带回来。
- **防过拟合检查**：别名表不是从评测集题目里整理出来的；上线前确认过 60 题的过滤条件都不会排除 gold 主位置。
- **已知局限**：问题里没有写公司名时（例如只说"这家公司"），不会做任何过滤；多轮对话的指代要到阶段 7 由 Agent 处理。

## D-015 实验结论的显著性口径（阶段 5）

- 评测集只有 52 道检索题，一题的变化就会让 Hit@5 变动约 0.019，所以不能只比平均值。
- `eval/compare_runs.py` 对两次实验做**配对 bootstrap**（1 万次重抽样，固定种子）和**符号检验**。
- **口径**：均值差的 95% 置信区间不跨 0，才称为"确定提升/下降"；否则写成"方向为正（或负）但不显著"。README 和简历里只写满足这个口径的结论。

## D-016 评测集措辞偏向与 v2 改写子集（阶段 5）

- **现象**：E004（过滤 + 只用 BM25）的 Recall@5 = 0.9006，确定高于 E003（过滤 + dense + BM25）的 0.7468。
- **怀疑**：v1 的题目是对照原文起草的，问题里直接用了原文的指标名，这对按词匹配的 BM25 有利。
  如果直接据此放弃 dense，结论可能只对"原文措辞"成立，换成口语化的问法就不成立了。
- **做法**：新建 v2 = v1 原题 + 60 道口语化改写题（只改措辞，公司和年份不变），在改写子集上重跑 E001~E004 的配置，
  用两个子集共同决定阶段 5 的基线。

## D-017 阶段 5 基线改为"过滤 + dense + BM25"，此后在 v2 上评测（阶段 5）

- **依据**（E001~E008，Hit@5，原题 / 口语改写）：
  | 配置 | 原题 | 改写 |
  |---|---|---|
  | dense | 0.6538 | 0.6154 |
  | 过滤 + dense | 0.6731 | 0.6154 |
  | 过滤 + dense + BM25 | 0.8462 | 0.5962 |
  | 过滤 + 仅 BM25 | 0.9423 | 0.4038 |
  - 仅 BM25 在改写题上确定差于 dense（E006→E008，Hit@5 −0.2115，CI [−0.3654, −0.0577]），也确定差于混合（E008→E007，+0.1923）；
  - 混合检索在改写题上与 dense 无显著差异，在原题上确定优于 dense（E002→E003，Hit@5 +0.1731）。
  - 结论：混合检索是**唯一一个在两种措辞下都不显著落后**的配置；仅 BM25 的高分来自 v1 的措辞偏向。
- **此后的评测口径**（事先定下，不根据结果再改）：
  - 每个实验都在 v2 全量上运行（104 道检索题），同时看 original / paraphrase 两个子集；
  - 主指标 Recall@5（覆盖多证据题），辅助指标 Hit@5、MRR@10；
  - **保留一项改动的条件**：v2 全量上 Recall@5 的差值为正，且在任何一个子集上都不是"确定下降"；
  - 写进 README 的"确定提升"仍然要求 95% 置信区间不跨 0（D-015）。

## D-018 重排：本地 bge-reranker-v2-m3 + 预留 API 开关（阶段 5，E015）

- **选择**：实验阶段用本地模型（FlagEmbedding，MPS），配置里预留 `RERANKER__PROVIDER=local | api`，API 版本到部署阶段按需接入。
- **理由**：
  - 本地模型文件固定、哈希校验过，E015 半年后重跑结果不变；托管接口可能悄悄升级模型或调整截断，历史实验就对不上了；
  - 每题重排 50 个候选，消融实验要跑多轮，本地运行没有限流和网络抖动（本机访问海外服务需要走代理，速度不稳定）；
  - 部署到无 GPU 的小服务器时，本地重排会很慢，那时切到 API 更实际。
- **不是理由**：数据隐私。本项目用的是公开年报。
- **下载**：与 bge-m3 一样从 ModelScope 下载，只取推理需要的 6 个文件（约 2.29GB），用 HuggingFace 公布的哈希校验。
- **max_length=1024**：FlagReranker 默认对"问题 + 段落"截断到 512 token，而 chunk 本身约 500 字，放宽以免截掉段落末尾。
- **重排输入用去实体后的检索文本**：与召回保持一致，理由见 BC-005。

## D-019 阶段 5 总结：最终检索配置与消融结果（阶段 5）

- **最终配置 = E013**：parser v1（去页眉页脚）+ fixed 切分（500/50）+ 公司/年份过滤 + 检索文本去实体
  + dense / BM25 / bge-m3 sparse 三路召回（每路 top_n=50）+ RRF（k=60），不重排。
  v2 全量 Recall@5 = 0.7869（原题 0.8846 / 口语改写 0.6891），Hit@5 = 0.8365，MRR@10 = 0.6532；检索延迟 p50 约 60ms。
- **逐步叠加**（v2 口径，保留规则见 D-017）：
  | 实验 | 改动 | Recall@5 | 相对上一步 | 处理 |
  |---|---|---|---|---|
  | E009 | 基线：过滤 + dense + BM25 | 0.6266 | — | — |
  | E010 | + sparse | 0.6474 | +0.0208 不显著 | 保留 |
  | E011 | + 去页眉（单独） | 0.3638 | −0.2837 确定下降 | 不保留，追查出 BC-005 |
  | E012 | E010 + 去实体 | 0.7708 | +0.1234 **确定提升** | 保留 |
  | E013 | + 去页眉 | 0.7869 | +0.0160 不显著 | 保留 |
  | E014 | + block 切分 | 0.7260 | −0.0609；原题子集确定下降 | 不保留（BC-006） |
  | E015 | + 重排 | 0.7804 | −0.0064 不显著 | 不保留；Recall@10 +0.0481（CI [−0.0016, +0.1042]），延迟 p50 1.9s |
- **逐个移除**（相对 E013 的 Recall@5 贡献；E011、E012、E016~E019）：
  过滤（连同去实体）+0.4696 确定；去实体 +0.4231 确定；去页眉 +0.0160、dense +0.0208、BM25 +0.0096、sparse −0.0112，均不显著。
- **结论**：
  1. 对年报问答，**查询理解（过滤 + 去实体）是决定性的**，远大于召回通道、切分或重排的选择；
  2. 在查询理解就位后，三路召回相互冗余，单独去掉任何一路在 104 题上都分辨不出差异；
  3. 仅 BM25 在原题措辞上最好、在口语改写上最差（E004 vs E008），说明评测集措辞会系统性地影响方法选择。
- **局限（写进 README 前必须说明）**：
  - 19 次实验、所有取舍都在同一份评测集（v1/v2）上做出，存在"在评测集上挑选"的偏差；v2 的改写题也由 AI 生成。
    在没有独立的留出集之前，E013 的绝对数值会偏乐观。建议：在阶段 6 前后准备一份不参与任何调参的留出集（v3），只用来报告最终数字。
  - sparse 在逐个移除中方向为负但不显著，可作为"简化候选"（少一路召回、少一次编码），留待留出集验证，不在本阶段根据同一份数据回头修改。
  - 重排对 Recall@10 方向为正且接近显著；阶段 6 若生成时使用前 10 个 chunk，需在生成指标上重新评估，不在此处改规则。

## D-020 生成与评审的模型设置（阶段 6）

- **生成**：DeepSeek `deepseek-flash`（DeepSeek-V4.1-Flash），OpenAI 兼容接口 `https://api.deepseek.com`，
  **关闭思考模式**（`extra_body={"thinking": {"type": "disabled"}}`，DeepSeek 默认开启），temperature=0，JSON 输出。
  - 理由：结果更稳定、更快（G001 生成延迟 p50 约 1.0s）、更便宜；思考模式下不能设置 temperature。开启思考可作为后续实验。
  - 以上参数都已对照 DeepSeek 官方文档核实（2026-09-27），并用一次最小请求验证过。
- **评审**：`deepseek-v4-pro`（关闭思考，temperature=0）。与生成模型不同、能力更强，减轻自我偏好；价格约为 flash 的 4 倍，但总量小。
- **缓存**：本地按请求哈希缓存响应（`data/cache/llm/`），重跑评测时不重复调用；改提示词或参数会自然得到新的缓存键。
- **费用**：按高峰价估算写入 `gen_log.csv` 的 cost_usd（只统计本次真实调用，不含缓存命中）。G001 全量 120 题（生成 + 评审）约 $0.25。

## D-021 评审 v1 的缺陷与 v2 修正（阶段 6）

- **发现**：G001 中评审（judge-v1）与规则判分在数值题上的一致率为 0.9359（78 题中 5 题不一致）。逐题检查后：
  - q102、q139、q143：评审理由写"与参考答案不一致，应判 0 分"，输出的分数却是 2——**分数与理由自相矛盾**；
  - q044：系统拒答，评审认为"证据不足、拒答合理"给了 2 分，**违反评分标准**（参考答案有明确答案时拒答应判 0）；
  - q112：系统答了数字但没有单位（该表的"千元"单位写在表头，没有进入同一个 chunk），评审给 2 偏宽。
  - 因此 **G001 的 judge_correct = 0.9500 虚高，不可采信**。G001 这一行保留在 gen_log.csv 中，不修改。
- **修正（judge-v2）**：
  1. 拒答、未作答由规则直接判定（`eval/judge.py` 的 `rule_verdict`），不调用大模型；
  2. JSON 字段改为先 reason 后 correctness，并要求分数与理由一致；
  3. "只写数字、没有单位或单位与证据不符"最多给 1 分。
- **教训**：LLM 评审本身是一个需要被评测的组件。规则判分与评审的一致率，是发现评审问题的最直接信号。
- **评审 v2 的校验**（G002，同一批答案）：
  - 由大模型评审的数值题共 72 道，评审与规则判分的一致率 0.9861（v1 为 0.9359）；剩下的 1 道（q045）是规则判错：
    模型用了茅台的"主营业务收入"168,774,585,187.65 元，与参考的营业收入只差 0.04%，落在规则 1% 的容差内被判命中，
    评审识别出口径不同给了 1 分。**规则判分分辨不了"数值接近但口径不同"**。
  - 随机抽查 20 条大模型评审结果（seed=0），20 条都符合评分标准。注意：抽查由 AI 完成，不是独立的人工审核。
  - 量化 v1 的虚高：同一批答案，G001（v1）→ G002（v2）评审正确率 −0.0458，CI [−0.0833, −0.0167]，确定下降。

## D-026 阶段 7 的 Agent 设计（2026-09-28）

- **目标**：v3 的失败里，表格读错行列（BC-012）、单位换算错（BC-008）、不肯计算（BC-007）、计算错误（q372）占了主要部分；
  另外单轮系统无法处理"那五粮液呢？"这类追问（D-014 的局限）。这些问题更适合交给工具和对话记忆解决，而不是继续改提示词。
- **图结构：固定骨架 + 工具循环**（`agent/graph.py`）：rewrite → retrieve（E013，前 10 个 chunk）→ agent ⇄ tools（最多 4 步）→ answer → verify。
  - 为什么不用纯 ReAct（完全由模型决定是否检索）：固定先检索，起点与 G002 完全相同，简单题上不会因为模型"忘了检索"而变差；调用次数更可控。
  - 代价：即使不需要工具，也比 G002 多一次模型调用（取证判断），延迟约翻倍。
  - 作答单独一个节点、用 JSON 模式输出，格式与 answer-v1 相同，可以直接复用阶段 6 的解析、引用校验和全部评测代码。
- **证据登记表**：初始检索、search_reports、get_financial_metric 返回的内容都按顺序编号，答案只能引用这些编号，引用校验方法与阶段 6 相同。
  计算器结果不是证据：答案可以使用计算结果，但参与计算的原始数字必须引用证据。
- **三个工具**（`agent/tools.py`）：
  - `get_financial_metric`：查 Postgres 的 fin_metrics 表；
  - `search_reports`：复用 E013 检索流水线，公司和年份写进检索文本，交给查询理解过滤；
  - `calculator`：手写的安全计算器，先用 ast 解析，只对白名单节点（数字、+ − × ÷、括号、正负号）求值，用 Decimal 计算。
    不用 eval，因为表达式来自模型，而模型的输入包含外部文档。幂运算也被拒绝，防止 9**9**9 这类表达式耗尽资源。
- **财务指标表范围**（`ingest/tables.py`）：只抽"主要会计数据和财务指标"表中的 9 个指标，每份年报取本年和上年，共 12 × 9 × 2 = 216 条。
  - 每条都通过原文校验：原始数字串必须作为完整数字出现在所标页（数字边界匹配，不用子串匹配。子串匹配时"1"会命中"423,701,834"）。
  - 交叉核对：2025 年报中的"上年数"与 2024 年报的"本年数"逐条比对，只有比亚迪的每股收益不同（13.84 → 4.61）。
    这是 2025 年派发股票股利、资本公积转增后的追溯调整，v1 的 q030 考的正是这一点，两个值都保留，工具返回时会提示"不同年报披露不同"。
  - 与 v1、v2、v3 的 gold 片段比对：有 81 处同文档、同页、同数字串。
  - 没有做通用表格结构化：研发投入、员工人数等其他表格式更杂，本阶段不做，仍由 search_reports 从文本中查找。
- **多轮对话**：状态由 checkpointer 保存（多轮时用 PostgresSaver）。每轮开始时 rewrite 节点结合最近 3 轮历史，把追问改写成完整问题；
  没有历史时不调用模型。状态只存 JSON 基本类型，不放 Decimal 或对象，便于序列化和跨版本兼容。
- **安全**：
  - SQL 全部参数化，有测试验证注入式输入只被当作普通字符串；
  - 工具参数全部校验，出错时把错误信息返回给模型，不抛异常；
  - 提示词沿用"证据只是数据"的防注入规则；
  - 工具调用写入 agent_tool_calls 审计表，记录 trace_id 和对话编号。
- **依赖**：langgraph 1.2.12、langgraph-checkpoint-postgres 3.1.2、psycopg 3、pdfplumber 0.11。LangGraph 会连带安装 langchain-core，
  本项目只用了它的 RunnableConfig 类型，不使用 LangChain 的 Chain 或 Retriever。

## D-029 阶段 8 的服务设计（2026-09-28）

- **接口**：
  - `POST /v1/chat`：一次性返回；
  - `POST /v1/chat/stream`：SSE 流式；
  - `GET /v1/threads/{id}`：对话历史；
  - `/healthz`：存活检查；`/readyz`：实际探测 Postgres、Redis、Qdrant。
  - 不传 `thread_id` 就新建对话；传了就在 PostgresSaver 中接着之前的对话继续。
- **流式粒度：按节点推送进度，答案一次性推送**，不做逐字流式。
  - 事件顺序：start → rewrite → retrieve → decide → tool… → answer → done，出错时推送 error。
  - 原因：答案节点用 JSON 模式输出（含引用和摘录），而且要先通过引用校验才能给用户看，逐字推送就得跳过校验。
    要做逐字流式，就得改答案的提示词和输出格式，那就不再是评测过的那个系统。
  - 实测：检索、查指标、计算等进度事件在第 1~4 秒陆续到达，答案约在第 5.8 秒到达（1 题，不开缓存）。
- **同步图放进线程池运行**：大模型调用层和嵌入模型都是同步的，接口用普通 def 定义，由 FastAPI 放进线程池；SSE 使用 FastAPI 0.135 起内置的
  `fastapi.sse`，同步生成器同样在线程池中迭代，框架会自动发送保活注释。检索和页面文本在 `build_deps` 里加锁，评测和服务共用同一套锁。
- **并发名额**：同时运行的 Agent 数有上限，默认 8，满了直接返回 503，不排队。
  - 名额在 yield 依赖里占用和归还。原因：FastAPI 先解析依赖、再校验请求体，用普通依赖的话，422 时名额会泄漏；
    有测试覆盖这一点，改回普通依赖后该测试会失败。
- **限流**：Redis 固定窗口计数（INCR + EXPIRE），默认每客户端每 60 秒 30 次。
  - 客户端按 API Key 的哈希区分，没有 Key 时按 IP。
  - Redis 不可用时放行（fail open），并记录警告，由 `/readyz` 暴露异常。限流是保护措施，不应该因为它故障而让服务整体不可用。
  - 鉴权在限流之前：没通过鉴权的请求不占限流额度。
- **鉴权**：可选的 `X-API-Key`，`API__KEYS` 可以配多个，用 `hmac.compare_digest` 比较。未配置时不校验，只用于本地开发；阶段 10 部署到公网时必须配置。
- **错误**：统一格式 `{"error": {code, message, trace_id}}`；对外不暴露堆栈、上游地址、异常详情，完整异常只写进服务端日志。
  大模型接口在重试用尽后仍失败，返回 502（流式接口里是 error 事件）。
- **trace_id**：客户端传了合法的 `X-Request-ID` 就沿用，否则新生成；响应头返回 `X-Trace-Id`。
  中间件用纯 ASGI 写，不用 BaseHTTPMiddleware（它和流式响应配合有已知问题）。
  trace_id 存在 contextvars 中，会传到线程池里的 Agent 和工具审计记录；有测试验证，实测审计表中的 trace_id 与响应头一致。
- **大模型缓存**：服务默认关闭（`API__LLM_CACHE=false`）；评测开启缓存，保证可复现。
- **Redis 端口**：宿主机 6379 已被其他项目的 Redis 占用，开发用 Redis 映射到 6380，并设置了密码（`REDIS_PASSWORD`，只写在 .env 里）。
- **验证**：
  - 一致性回归：开启缓存后，通过 API 问 v2 的 10 道题（覆盖指标工具、计算、比较、检索工具、拒答），答案、拒答判断、引用和工具序列
    与 G007 的明细 10/10 一致，说明服务层没有改变系统行为；
  - 真实调用冒烟：SSE 事件流、同一 thread 的追问改写、历史查询、422/404 错误格式都正常；4 个并发请求全部成功，
    单题耗时 3.1~5.6 秒，总耗时 5.6 秒。样本太少，正式压测在阶段 11。
- **已知局限**：
  - 客户端中途断开时，正在线程池中执行的这一步（例如一次模型调用）不会被中断，只是之后不再继续推送；并发名额由 yield 依赖兜底归还；
  - 固定窗口限流在窗口交界处最多可能放行 2 倍的请求；
  - 单进程部署：多进程或多实例时，嵌入模型会各自加载一份，并发名额也是按进程计的（阶段 10、11 再考虑）。

## D-030 阶段 9 的前端设计（2026-09-28）

- **布局**：
  - 侧边栏：新建对话、服务状态（/readyz）、语料清单；
  - 左栏：对话。提问后用状态框实时显示 SSE 进度，例如"检索到 10 段年报原文""查询财务指标：比亚迪 2024 年 营业收入""计算：…"；
  - 右栏：原文查看器。
- **点击引用看原文**：Streamlit 不方便让答案正文里的 `[n]` 直接可点，所以在答案下方逐条列出引用：公司、年份、页码、摘录，每条带"查看原文"按钮。
  点击后，右栏显示该页截图，摘录位置用黄色框高亮，支持上一页、下一页。
  - 没有通过核验的引用显示成灰色，并标注"未通过核验"，不提供查看原文；
  - 引用只定位到页码范围时（跨页 chunk），显示范围内的第一页。
- **前端只和 API 通信**（`ui/client.py`），不直接读 PDF、不连数据库：
  - 部署时两者可以分开，PDF 只需要放在服务端；
  - API Key 由 Streamlit 服务端读取，不会发到浏览器。
- **页面截图接口**：`GET /v1/documents/{doc_id}/pages/{page}/image?q=摘录`，由服务端渲染 PNG。
  - 响应头 `X-Highlight-Method`、`X-Highlight-Count` 告诉前端是否定位成功；
  - doc_id 只能是 manifest 中登记的文档，文件路径由服务端拼出（防路径穿越）。页码、摘录长度、缩放倍数都做了校验；
  - 只在内存里画框，不修改 PDF；渲染结果用 LRU 缓存（64 张）。
- **高亮定位**（`api/pages.py`），依次尝试三种方法：
  1. `search_for` 整段搜索；
  2. 逐字对齐：用和引用校验相同的归一化规则拼出页面文本，找到摘录后，把命中的字符按行合并成矩形，处理摘录跨行等情况；
  3. 数字兜底：取摘录中的长数字串做完整匹配。财务指标工具的摘录是生成的句子，不在 PDF 上，但其中的原始数字在。
  - 数字边界判断踩了和 D-026 相同的坑：去掉空白后，表格相邻两列的数字会粘在一起。
    这次单独记录"前面有间隔"（空白、换 span、换行）的字符位置，用它判断边界。修正前，68 条工具证据的引用全部定位失败。
  - **覆盖率**（G007 + G008 中全部 413 条通过核验的引用）：
    | 方法 | 条数 |
    |---|---|
    | exact 整段搜索 | 320 |
    | number 数字兜底 | 69 |
    | chars 逐字对齐 | 19 |
    | 定位失败 | 5 |
    - 合计 **408/413（98.8%）** 能画出高亮框；工具证据的 68 条全部能定位；
    - 5 条失败都是跨页 chunk 中跨过分页处的摘录，界面会提示"未能定位，可以翻页查看"。
- **验证**：
  - 单元测试：用测试里生成的中文 PDF 覆盖跨行、相邻数字列、数字兜底；接口测试覆盖路径穿越、页码越界、鉴权；
    用 AppTest 配合假客户端，对页面做冒烟测试（提问、查看原文、追问沿用对话编号）；
  - 端到端：真实启动 API 和 Streamlit，用浏览器操作了普通问题、工具问题、追问、拒答、查看原文和新建对话。
    高亮截图核对过：宁德时代 2025 年报第 24 页"营业收入合计"一行，6 个单元格各有一个框。
  - 端到端中发现并修复了两个布局问题：流式回答显示在输入框下方（改为先放对话容器、再放输入框）；"查看原文"按钮文字被截断。
- **局限**：
  - Streamlit 每次交互都会从头执行脚本，不适合复杂的交互；答案正文里的 `[n]` 不能直接点击；
  - 流式过程中不能中途取消；
  - 对话历史只保存在浏览器会话里，刷新页面就是新对话（服务端的 checkpoint 仍在，可以通过 /v1/threads 查询）。
